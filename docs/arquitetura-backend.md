# Arquitetura do backend

Registro das decisões que sustentam a passagem do protótipo (dados mock no navegador) para o app real
(Supabase + Vercel + um provedor de IA compatível com a OpenAI: Groq ou xAI). Cada decisão diz o que foi escolhido e **por quê**; o plano de fases está no
README e o contexto do produto em [especificacao-app-pessoal.md](especificacao-app-pessoal.md) e
[decisoes.md](decisoes.md).

Status: **aceitas em 2026-10-07**. Alterar uma delas exige atualizar este arquivo. As decisões 11 a 28 vieram durante a
implementação, cada uma com o problema real que a motivou.

## Princípios

1. **O domínio é puro e compartilhado.** `src/domain` não conhece React, banco nem rede. A tela, a atualização
   otimista, o modo demo e as ferramentas do assistente chamam as **mesmas** funções — por isso o número que a IA
   fala é, por construção, o da tela.
2. **O banco é a última linha de defesa.** Isolamento por usuário (RLS), integridade pai/filho, idempotência e
   regras como "uma sessão de estudo por vez" vivem no Postgres, não só no TypeScript.
3. **Nada de sucesso sem persistência.** Em modo real, o aviso de "salvo" só aparece depois da confirmação do servidor.
4. **A IA é opcional e nunca escreve.** Sem chave o app inteiro funciona; com chave, o modelo só *propõe*.

## Decisões

| # | Decisão | Por quê |
|---|---|---|
| 1 | **Ports & adapters em `src/data`**: um contrato de ações/leitura com dois adapters, `demo` (store local) e `remote` (Supabase). O modo é `NEXT_PUBLIC_APP_MODE=live\|demo`, **fixo por deploy** | A spec exige demo separado dos dados pessoais. Sem alternância em runtime, é impossível misturar. Mantém os fluxos E2E rodando sem backend |
| 2 | **Comandos tipados + reducers puros** (`domain/commands.ts`, `domain/reducers.ts`) | O mesmo reducer alimenta a atualização otimista, o adapter demo e o **teste de paridade** com o banco |
| 3 | **TanStack Query** guarda o estado de servidor (um `["snapshot"]`); zustand fica só com estado do aparelho (rascunho de treino, descanso, UI) | O domínio já consome um snapshot inteiro; para um dono, carregar tudo é viável |
| 4 | **Leitura** por `GET /api/snapshot` (Route Handler); **escrita** por Server Actions | O Next despacha Server Actions uma por vez por cliente; leitura nelas ficaria presa atrás de escritas |
| 5 | **Todo acesso a dados no servidor.** Sem cliente Supabase no navegador e **sem service role em lugar nenhum** | Superfície de ataque mínima: se uma chave vazar, não há chave poderosa. CSP com `connect-src 'self'` |
| 6 | **Auth** com `@supabase/ssr` + `proxy.ts` + `getClaims()`; cadastro desativado | O proxy é só checagem otimista. A autorização real é `requireUser()` em **cada** action/handler. Nunca `getSession()` no servidor |
| 7 | **Páginas não leem cookies.** O portão é o proxy + 401 do `/api/snapshot` | Com Cache Components, ler sessão num Server Component exige `<Suspense>` e dispara a validação `instant`; assim as rotas continuam shells estáticos |
| 8 | Operações **compostas ou idempotentes** = RPC `security invoker`; CRUD de uma linha = PostgREST sob RLS | Atomicidade e invariantes no banco, com RLS valendo dentro das funções |
| 9 | **Ids UUID v4 gerados no cliente**; `INSERT ... ON CONFLICT (id) DO NOTHING` | É a chave de idempotência: toque duplo ou nova tentativa não duplica. Substitui o `idempotency_key` da spec |
| 10 | **Cronômetro de estudo no servidor** (PK = `user_id`); **rascunho de treino local** | A spec proíbe duas sessões simultâneas entre dispositivos. Treino: sinal ruim na academia (decisão B) |

| 11 | **O token de redefinição de senha só é consumido no envio do formulário**, nunca ao abrir o link | Scanners de e-mail "clicam" nos links antes da pessoa e queimariam um token de uso único aberto por GET |
| 12 | **Catálogos nunca são apagados depois de usados: são arquivados** (categorias, exercícios, matérias, fichas). Livro é a exceção: exclui junto as leituras, com confirmação que diz quantas | Preserva o histórico (spec §12); arquivar libera o nome (índice único parcial) |
| 13 | **O assistente só PROPÕE.** O modelo escolhe ferramentas que executam as mesmas funções puras do domínio; o texto da proposta é fixo; o id da proposta vira o id do lançamento | O número da IA é o da tela por construção; confirmar duas vezes não duplica; prompt injection não consegue gravar nada |
| 14 | **Limites de IA no banco, atômicos, e a IA só é chamada depois deles; se não der para conferir, não chama (falha fechada)** | A IA custa dinheiro: um bug ou laço não pode virar gasto sem teto |
| 15 | **Service worker com política mínima**: só `/_next/static/*` e `/offline`; nunca HTML das telas, `/api/*`, RSC nem POST | Spec §13: nada financeiro ou de IA em cache; sair da conta não deixa dados no aparelho |
| 16 | **CSP estrita em produção** (`connect-src 'self'`, sem eval, sem terceiros). `unsafe-inline` em scripts por causa dos scripts inline do Next/tema; nonce quebraria as telas estáticas | O navegador nunca fala com o Supabase nem com a IA, então um script injetado não teria para onde enviar dados |
| 17 | **Configuração inválida derruba o build** (validação no `next.config.ts`), não a primeira requisição em produção | Falhar cedo e com a lista do que falta |
| 18 | **Um adaptador só para provedores compatíveis com a OpenAI** (`openai-compatible.ts`) e uma fábrica por env (`AI_PROVIDER` = `groq`, `xai` ou `none`; `AI_MODEL`, `AI_API_KEY`, `AI_BASE_URL`). Nomes de variável genéricos | Trocar de provedor é mudar variável, não código; uma `XAI_API_KEY` guardando chave da Groq seria enganosa. A Groq tem camada gratuita (com limite de tokens por minuto) e a xAI é paga |
| 19 | **O servidor entrega as datas prontas no prompt** (hoje, ontem, esta semana, semana passada, últimos 7/30 dias, este mês, mês passado), calculadas com as funções do app | Na avaliação com o modelo real, "esta semana" virou "2 a 8 de outubro" numa quarta-feira 7 (a semana vai de segunda 5 a domingo 11). Modelos erram aritmética de calendário; o servidor não |
| 20 | **Cookie de sessão `httpOnly` + `SameSite=Lax`, e `Secure` conforme o protocolo da requisição** | O @supabase/ssr grava `httpOnly: false` porque o cliente de navegador precisa ler; este app não tem esse cliente, então o JavaScript da página não deve enxergar o token. `Secure` por protocolo (não por ambiente) para o app seguir abrindo por http na rede local |
| 21 | **Corrida é uma entidade própria** (`running_sessions`), com distância e duração opcionais (NULL = "não informado", nunca zero) em metros e segundos inteiros | A musculação tem regras próprias (exige séries concluídas) e uma corrida registrada à mão não tem início, fim nem séries. Inteiros evitam divergência de arredondamento entre cadastro, meta, histórico e Home |
| 22 | **Data futura é recusada pelo banco**, num gatilho com `private.app_now()` e `app_tz()`; o reducer a recusa com o `nowMs` do comando, e o teste de paridade exige a mesma mensagem | O horário do aparelho nunca decide uma regra do servidor (um relógio adiantado não libera uma data futura), e inserir direto na tabela também é barrado |
| 23 | **O id de um registro novo nasce com o formulário e é reenviado em cada tentativa**, e uma falha desfaz a atualização otimista na hora (para vários comandos ao mesmo tempo, ver 28) | Bloquear toque duplo não cobre "o servidor salvou e a resposta se perdeu". E a releitura que reconcilia o cache falha justamente quando o servidor está fora do ar: sem o desfazer, o total otimista ficaria na tela |
| 24 | **Migração antes do app.** As migrações são aditivas; o app novo recusa um banco sem a coleção nova (com a mensagem de aplicar a migração) em vez de abrir pela metade | Ver o passo a passo em [setup-supabase.md](setup-supabase.md#atualizar-um-projeto-que-já-está-em-uso-ordem-de-implantação) |
| 25 | **Cards do assistente são REFERÊNCIAS, não dados.** O servidor responde com o texto e, por ferramenta que achou registros, só `{kind, mês/período}` (~80 bytes, fora do payload que vai ao modelo); o app monta o card com o próprio snapshot e as mesmas funções de domínio das telas (`domain/assistant-cards.ts`), e o demo usa o mesmo código | Zero token e zero chamada extra à IA, nenhuma tabela ou consulta nova, nenhum nome de categoria, matéria ou livro trafega a mais, e o modelo nunca produz interface (só `text`). O cliente valida as referências com Zod e descarta o que for inválido, mantendo o texto |
| 26 | **O nome de exibição é editado pela RPC `set_display_name` (security invoker) e validado em TRÊS camadas**: `parseDisplayName` em `domain/profile.ts` (normaliza e dá a mensagem; é a regra do formulário, da Server Action e do demo), a Server Action (autentica por `getClaims()` e trata o argumento como entrada não confiável) e um gatilho no banco (`private.check_profile_name`) que recusa o que não vier normalizado, por qualquer caminho. O cliente só tem `UPDATE (display_name)` em `profiles`; o dono da linha vem do `auth.uid()`, nunca do argumento | A API do Supabase continua acessível a quem tem um JWT válido, então uma regra só no TypeScript pode ser contornada com um PATCH direto. O gatilho só dispara em UPDATE e só quando o nome muda, para nunca barrar o cadastro (que deriva o nome do e-mail e pode gerar um nome vazio ou terminado em espaço). O que depende de propriedades Unicode (letra ou número, pilha de acentos) fica só no TypeScript, porque o Postgres não tem `\p{...}`; um teste prova que o banco **nunca recusa o que o app aceita** |
| 27 | **Água é um registro por toque** (`water_intakes`: `id`, `occurred_at`, `ml`), imutável (só nasce e é removido), com o **instante** guardado e o **dia derivado dele** no fuso do app (`dateKeyFromInstant` no cliente, `at time zone public.app_tz()` no SQL). O total do dia nunca é guardado. Só se registra água de **hoje e de ontem**, com até 5 min de folga no futuro, recusado por um gatilho que usa o relógio do servidor (mesma regra e mesmas mensagens do reducer, provadas pelo teste de paridade). A meta é o `GoalKind` `water_ml`: o `target` é **ml por dia**, com vigência semanal (segunda-feira), pelo mesmo mecanismo das outras metas. As três porções do contador e a escolhida ficam **só no aparelho** (`data/water-prefs.ts`, apagadas ao sair da conta) | Um contador agregado por dia não é idempotente (uma resposta perdida somaria duas vezes), não permite desfazer o toque exato e perde o horário (que alimenta o "ritmo do dia" e a sequência). O instante, e não só a data, faz um toque às 00h30 cair no dia novo nos dois lados. Reaproveitar a meta semanal evitou mexer na restrição de `valid_from` do banco. Preferências de três números não justificam tabela, comando e exportação. **Custo conhecido:** o snapshot carrega tudo (decisão 3) e ~12 toques por dia dão ~0,4 MB por ano; o limiar para revisar é passar de 1 MB de `waterIntakes` ou a Início levar mais de 100 ms para agregar, quando valerá compactar os dias antigos em linhas por dia (isso afetaria `AppData`, a paridade e o backup, então seria uma decisão própria) |
| 28 | **A camada otimista guarda o estado que o servidor já conhece e a lista do que está a caminho** (`data/remote/optimistic.ts`); quando um comando falha, a tela é refeita **sem ele e com os demais**, em vez de "voltar ao que era" | O desfazer da decisão 23 só rodava com um único comando em andamento. Num contador de um toque, toques seguidos são o caso comum: com o servidor fora do ar o total na tela ficava com os toques que não foram salvos (e a releitura que corrigiria falha justamente ali). Funciona para todos os comandos; as Server Actions saem em série, então a ordem é preservada |
| 29 | **A biblioteca de exercícios vive no código** (`domain/exercise-library.ts`, igual para todos) e o exercício da pessoa só guarda um **vínculo opcional** (`exercises.library_key`). O banco confere o formato da chave; a validação dos comandos confere se ela existe nesta versão do app. Chaves só são acrescentadas, nunca trocadas | Os exercícios continuam sendo da pessoa (nome e grupo dela, histórico com os nomes de quando foi feito). Uma tabela global no banco exigiria migração a cada exercício novo e políticas próprias, para um dado que é igual para todos e muda com o app. A biblioteca dá o equipamento (passo de carga da progressão), os músculos e o padrão de movimento: a base do plano de treino da fase 1 |
| 30 | **O snapshot declara a versão do esquema** (`schemaVersion`, desde a migração 16) e o app exige a sua (`SNAPSHOT_SCHEMA_VERSION`) | A detecção de implantação fora de ordem olhava só chaves novas do snapshot. Campos novos DENTRO de registros (o `effort` da sessão, o vínculo do exercício) passariam despercebidos, e o banco antigo os descartaria em silêncio ao gravar: o app diria que salvou o que não salvou. Com a versão, o app recusa abrir e diz qual migração falta |
| 31 | **Porta de assinatura (futuro, não implementada):** o app inteiro será pago, então a porta é **por conta**, num ponto só: `userFromClaims()` (server/auth-claims.ts), que já autoriza cada Server Action (`actions/commands.ts`, `actions/profile.ts`) e cada Route Handler (`/api/snapshot`, `/api/export`, `/api/assistant`), passa a devolver também o estado da assinatura, e quem não tem assinatura ativa recebe "não autorizado" ali mesmo (a assinatura vem de uma tabela atualizada pelo webhook do meio de pagamento, nunca do cliente). O proxy (`decideAccess`) redireciona para a tela de assinatura, só como atalho visual. As funções de IA (assistente e plano de treino) passam por `ai_reserve`, que é onde entram limites por plano, se um dia houver | Uma porta por tela ou por função espalharia a regra e abriria brechas (uma rota esquecida). O ponto único que já autoriza tudo é o lugar natural; nada da fase 0 precisa saber de pagamento |
| 32 | **Plano de treino: regras montam, IA escolhe dentro, validação confere** (`domain/training-rules.ts`, `server/ai/plan.ts`). As regras geram o esqueleto (divisão, vagas, séries, faixas, tempo e a lista fechada de exercícios de cada vaga); a IA responde em **saída estruturada estrita** com um JSON Schema gerado a cada pedido, em que as opções de cada vaga são `enum`; `planErrors` confere o que o schema não alcança (exercício repetido no treino, tempo). Uma nova tentativa com os erros; depois disso, ou com o provedor fora/no limite, o plano sai das próprias regras (`rulesProposal`) | A IA faz o que faz bem (escolher entre opções conhecidas, priorizar o que a pessoa já faz, explicar) e o código garante o que não pode falhar (volume, tempo, segurança). Com enum no schema, inventar exercício é impossível na decodificação, não só proibido no prompt. Há sempre um plano válido, com ou sem IA: o demo usa o mesmo caminho do modelo pronto. Um teste percorre todas as combinações de respostas e exige plano válido em todas |
| 33 | **A proposta vive no aparelho; só o plano ACEITO vai ao banco, num comando atômico** (`training.applyPlan`, migração 17). O comando cria os exercícios que faltam, as fichas, arquiva as escolhidas e grava o registro do plano, reaproveitando os comandos `exercise.add`, `plan.save` e `plan.archive` (no reducer e no SQL), com as mesmas mensagens; é idempotente pelo id do plano. O registro é um documento (`details` jsonb, até 32 KB) com colunas só para o que o banco precisa (id, instante, origem) | Gerar e trocar não sujam o banco nem precisam de idempotência no servidor; aceitar pela metade (exercícios criados, fichas não) seria pior que falhar. O documento evita uma tabela por detalhe de um registro que é imutável e só é lido inteiro; o app valida o formato ao entrar (schema do comando) e ao sair (snapshot) |
| 34 | **Dados de saúde do plano: só com consentimento, e só o necessário.** `training_profiles` só aceita limitações com o instante do consentimento (CHECK no banco); a triagem guarda só o resultado, nunca as respostas; o registro do plano aceito leva as respostas SEM a parte de saúde; para a IA vão as regiões marcadas e o resultado da triagem, sem nome nem e-mail | Minimização (LGPD, art. 6º, III) e consentimento específico para dado sensível (art. 11, I). Apagar a parte de saúde é refazer as perguntas pulando-a: uma linha por pessoa, substituída |
| 35 | **Dias por semana ≠ número de treinos** (`domain/training-splits.ts`): um catálogo fechado de divisões (de AB a ABCDEF) e um padrão por dias e experiência (5 dias → 3 treinos em rodízio); a divisão escolhida vive na proposta e no `details` do plano aceito (`option`), sem migração. `timesPerWeek` é fracionário (dias ÷ treinos) e as regras sobem séries dos grupos grandes que ficariam abaixo do mínimo semanal | A pessoa recebia 5 treinos diferentes sem aviso. Quem não quer pensar recebe o padrão escrito em português simples ("3 treinos que se revezam nos seus 5 dias"); quem quer escolhe entre opções válidas. O volume da semana pesa mais que a frequência (Schoenfeld et al., 2019), por isso a divisão muda as séries, não só os nomes |
| 36 | **Base científica fixa no código** (`domain/training-evidence.ts`): 8 princípios com referência completa e DOI. A seção "Por que este treino funciona" é montada pelas regras; nos ajustes, a IA só aponta o id de um princípio (enum no schema) | A IA não consegue inventar estudo. Zero token para a seção. As frases e referências passam por revisão de um profissional antes de abrir o app a outras pessoas |
| 37 | **Ajustes sem refazer o formulário** (`domain/training-adjust.ts`): toda mudança é uma operação pequena (trocar, séries, repetições, mover, remover) aplicada pelas MESMAS funções das edições à mão; os chips viram operações pelas regras (sem IA); o texto livre vai à IA (`/api/training/plan/adjust`, schema estrito, até 3 mudanças, 1 tentativa, 900 tokens de saída); tudo passa por uma prévia de antes → depois | Uma sugestão inválida, venha de onde vier, é descartada antes da tela. O caminho comum (chips) não custa nada; o texto livre custa ~US$ 0,0002–0,0003 por pedido (1,4–2,8 mil tokens de entrada medidos). O texto da pessoa não vai para log nem banco |
| 38 | **Ajuste no plano EM USO = fichas + histórico, num comando atômico** (`training.adjustPlan`, migração 18). As fichas atuais são lidas como um rascunho virtual (`domain/training-current.ts`), encaixando cada exercício numa vaga das regras; o que não encaixa (fora da biblioteca, repetido) fica fixo e volta à mesma posição. O registro (`training_plan_changes`) guarda o que a pessoa viu na prévia (onde, antes, depois, motivo, princípio), o gatilho e a origem, nunca o texto livre | Os mesmos ajustes e validações do rascunho valem para o plano em uso, sem uma segunda implementação. O histórico é a base da revisão a cada 4 semanas (fase 2). Sem "Desfazer" (já está no banco): por isso a prévia é obrigatória |
| 39 | **Volume semanal por regra, só quando há motivo** (`domain/training-focus.ts`, `training-volume.ts`). Mede-se a **série efetiva por músculo** (direta = 1, indireta = 0,5: o tríceps no supino, o bíceps na remada; o ombro não recebe crédito do supino). O foco só mexe no volume se há lacuna e **depende do objetivo**: massa leva o grupo à faixa de foco (intermediário: 18 séries efetivas por semana), com peso e contrapeso (nunca corta o foco nem quem lhe dá trabalho indireto; o resto desce no máximo ao piso de manutenção, ~1/3 do volume normal); força só ganha uma série pesada no exercício principal; saúde e emagrecer, até 2 séries; iniciante e liberação médica pendente ficam no topo da faixa normal; região com dor marcada nunca é reforçada. A mesma função (`runFocus`) monta o plano e ajusta o plano que existe (`focusAdjustment`), inclusive acrescentando exercício. A IA **só escolhe exercícios** (o schema não tem mais séries nem repetições) e, no texto livre, só diz QUAL grupo reforçar. Sem foco e sem lacuna, **nada muda**: um teste compara os planos de 960 combinações sem foco com uma impressão digital anterior à mudança. As faixas são propostas calibradas pelos planos padrão e precisam de revisão profissional | O pedido "foco em peito" produzia só 2 exercícios de peito a mais e, nos braços, zerava o bíceps (o corte de tempo tirava justo os exercícios de prioridade 3 do grupo em foco). Volume decidido pela IA varia de uma geração para outra; decidido por regra é previsível, testável em todas as combinações e custa zero token (a saída da IA ainda encolhe). O volume é o que mais explica o ganho de massa, com retorno decrescente (Schoenfeld et al., 2017; Pelland et al., 2024, pré-print), mas para força importa a carga (por isso o foco não infla o volume por músculo) e 1/3 do volume mantém o que já foi ganho (Bickel et al., 2011, adultos jovens; o app ainda não conhece a idade). **Observação deixada de fora de propósito:** a regra antiga de mínimo semanal (6/10/12 séries por grupo) continua valendo para TODOS os objetivos, inclusive saúde e emagrecer; mudá-la alteraria planos de quem não pediu nada, e fica como decisão à parte |

## Onde cada coisa mora

```
src/domain/     regras puras (dinheiro, períodos, metas, resumos) + commands/reducers
src/data/       a única porta de entrada das telas: demo/ (local) e remote/ (servidor)
src/server/     server-only: env, auth (requireUser), supabase, mappers, handlers, ai/
src/app/api/    snapshot, assistant, export, health, cron
supabase/       migrations SQL, testes de banco
```

## Variáveis de ambiente

Validadas com Zod em [src/server/env.ts](../src/server/env.ts) e checadas na subida do servidor
(`src/instrumentation.ts`): uma variável faltando derruba o deploy com a lista do que falta. A lista completa,
com o que é obrigatório em cada modo, está em [.env.example](../.env.example).

## Qualidade

- **Gate de CI** (`.github/workflows/ci.yml`): lint, typecheck, testes (inclui banco), `npm audit` de produção, build,
  E2E em modo demo, **E2E em modo live** (app real contra um Supabase e uma API de IA falsos) e varredura de segredos.
- **Teste de paridade**: para cada comando, `applyCommand(snapshot, cmd)` tem de ser igual ao snapshot lido do banco
  depois de executar o mesmo comando. Pega divergência entre o TypeScript e o SQL.
- **Banco**: RLS com dois usuários, constraints, idempotência e virada de dia no fuso, em PGlite (sem Docker). Travas
  que quebram se aparecer: tabela sem RLS, função aberta a quem não está logado, `security definer` desconhecida.
- **Teste de mutação manual**: ao escrever as regras de SQL e do service worker, cada regra crítica foi quebrada de
  propósito para confirmar que algum teste falha.
- **Fakes de infraestrutura** (`e2e/fake-supabase.mjs`, `e2e/fake-xai.mjs`, este último uma API compatível com a OpenAI): Auth + PostgREST sobre as migrações reais e
  uma API compatível com a da OpenAI. Provam a integração sem chaves; **não substituem** um teste contra os serviços de
  verdade. Esse teste foi feito em 2026-10-07 (Supabase e Groq reais, com um usuário descartável criado e apagado por um
  script fora do repositório): migrações, RLS, login com cookie `httpOnly`, persistência e assistente passaram.
